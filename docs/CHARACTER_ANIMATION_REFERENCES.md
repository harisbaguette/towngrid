# 캐릭터 움직임 개선: 참고 자료와 적용안

롤백한 캐릭터의 얼굴·체형·의상·픽셀 화풍은 유지한다. 해결 대상은 **움직일 때의 형태 붕괴, 지형과의 접촉, 방향·동작·캐릭터 사이의 일관성**이다. 아래는 제작 자료와 현재 코드를 대조한 개선안이며, 동작 개선이 적용됐다는 뜻은 아니다. 전체 대상은 [캐릭터 동작 체크리스트](CHARACTER_ANIMATION_CHECKLIST.md)의 51명·11개 동작·네 방향이다.

## 1. 팔·다리·몸통의 움직임

### 참고 자료에서 확인한 방법

- [Dan the Man 제작자 Toni의 픽셀 애니메이션 설명](https://esotericsoftware.com/forum/d/7532-using-spine-with-pixelart-in-dan-the-man): 기존 프레임별 픽셀 작화에 맞추려고 커스텀 캐릭터의 메시 변형과 자동 보간 사용을 제한했다. 오래 보이는 대기·공격 마무리 자세에는 부품을 새로 그렸으며, 직접 그린 동작과 골격 동작을 GIF로 비교한다. 횡스크롤 게임 사례이므로 보행 방향이나 카메라 규격까지 가져올 자료는 아니다.
- [Spine 공식: 새로운 자세 작화 연결](https://en.esotericsoftware.com/blog/Rigging-new-poses-tutorial): 동작 도중 다른 각도의 몸통이나 손이 필요하면 추가 그림을 제작해 교체한다. 골격을 사용해도 한 장의 그림만으로 모든 자세를 표현하지 않는다. 도구 도입 권고가 아니라 자세별 작화가 필요한 이유를 보여 주는 자료다.
- [SLYNYRD: Human Walk Cycle](https://www.slynyrd.com/blog/2024/5/24/pixelblog-50-human-walk-cycle): 실제 보행을 참고해 전신 러프를 먼저 완성하고, 착지·체중 받기·다리 통과·다음 발 내밀기를 연결한다. 팔과 반대쪽 다리의 관계, 의상의 주름 방향도 연속적으로 맞춘다. 글의 프레임 수는 해당 작품의 선택이다.
- [Animation Mentor: Human Walk Cycle](https://www.animationmentor.com/blog/tutorial-animating-human-walk-cycle/): 골반과 가슴의 반대 회전, 어깨→아래팔→손목의 지연, 이동 후 정지까지 다룬다. 시연 도구는 Maya지만 참고할 내용은 전신의 운동 원리다.

### 현재 코드에서 확인되는 한계

`scripts/mira_rig.py`와 `scripts/roster_rig.py`의 일반 보행은 몸통 그림을 통째로 평행 이동한다. 가슴과 골반을 서로 다르게 돌리는 자세 작화가 없다. `scripts/character_body_motion.py`의 `walking_hand`가 손끝을 움직이고 공통 관절 계산으로 팔꿈치를 정한다. 어깨·아래팔·손목을 각각 조절하는 보행 연기는 없다.

`scripts/rig_skinning.py`는 원래 팔·다리 그림을 삼각형으로 변형한다. 관절 좌표가 맞아도 소매·손·무릎의 실루엣과 픽셀 덩어리까지 자연스럽게 유지된다는 보장은 없다. 팔의 합성 순서도 기본적으로 먼 팔→몸통→가까운 팔로 고정돼 있다. 특정 자세에 필요한 가림 변화는 별도 작화나 순서 지정이 필요하다. 모든 프레임에서 이 순서가 틀렸다는 뜻은 아니다.

### TownGrid 적용안

1. 기존 캐릭터를 기준으로 **전신 동작의 연속 러프와 최종 프레임별 작화**를 만든다. 착지 순간의 골반·가슴·어깨·팔·양발을 한 자세로 설계한다.
2. 팔꿈치가 크게 접히거나 몸을 가로지르는 자세, 손바닥 방향, 굽은 무릎, 회전한 몸통은 필요한 그림을 새로 그린다. 늘어난 텍스처를 최종 작화로 쓰지 않는다.
3. 좌우 보행의 같은 시점을 나란히 비교한다. 체중을 받는 다리와 반대쪽 팔, 팔꿈치·손목의 이어짐, 몸 뒤에 들어갔다 나오는 손을 확인한다.
4. 걷기·운반·직업 작업·공격은 각각의 전신 동작으로 만든다. 운반은 손과 짐의 접촉, 상하차는 무게를 받는 자세까지 포함한다.
5. 필요한 중간 자세를 추가한다. 장수는 8·16·32 중 하나로 미리 고정하지 않고, 같은 주기 시간에서 실제 재생으로 정한다. 전체 이미지의 반투명 겹치기는 두 팔다리가 보일 수 있어 전환 작화를 대신하지 않는다.

## 2. 발과 지형의 결합

### 참고 자료에서 확인한 방법

[Spine 공식 Ghosting의 Offset 설명](https://esotericsoftware.com/spine-ghosting#Offset)은 실제 이동 속도만큼 연속 자세를 옮겨 겹쳐 보고 지지발이 같은 곳에 남는지 확인한다. 제자리 걷기만 보는 것보다 실제 이동 중 미끄러짐을 직접 확인할 수 있다.

[Unity 공식 Sprite Renderer](https://docs.unity.com/en-us/engine/6000.5/manual/unity2d/sprite/sprite-renderer-reference)와 [그리기 순서 설명](https://docs.unity3d.com/6000.0/Documentation/Manual/sprite/sort-sprites/sort-sprites.html)은 그림의 기준점과 앞뒤 정렬을 구분한다. TownGrid는 Three.js의 깊이 검사도 사용하므로 Unity 설정을 그대로 옮기지 않고, 실제 발 기준점·지면 높이·가림 판정을 각각 확인해야 한다.

### 이미 있는 기능과 아직 확인할 부분

- `character-movement.js`와 `character-motion-state.js`는 실제 이동 거리와 `strideLength`로 보행 프레임을 진행한다. 실거리 동기화가 없는 상태가 아니다.
- `pixel-terrain.js`의 `terrainHeightAt`은 캐릭터 중심이 속한 칸에서 흙·도로·철도·관/컨베이어의 높이를 고른다. 두 발이 서로 다른 표면에 걸치는 상태는 직접 계산하지 않는다.
- `sprite-grounding.js`는 화면을 향한 스프라이트 평면을 카메라 쪽으로 이동시켜 바닥 관통을 피한다. 이 보정이 실제 건물·자연물 경계에서 어떻게 보이는지는 별도 재현이 필요하다.
- 현재 코드만으로 사용자가 본 모든 지형 문제의 원인을 확정할 수 없다. **그림 안의 발 궤적, 이동과의 불일치, 높이 경계, 잘못된 가림**을 분리해 확인한다.

### TownGrid 적용안

1. 같은 동작을 투명 배경→눈금 바닥→실제 지형에서 재생해 문제가 처음 생기는 단계를 찾는다.
2. 프레임마다 좌우 발의 뒤꿈치·발끝과 접촉 구간을 기록한다. 접지 검사는 각 발을 따로 추적하고, 디딘 동안 실제 지지점이 월드에서 밀리는지 측정한다. 뒤꿈치에서 발끝으로 체중이 넘어갈 때 발목까지 고정하지 않는다.
3. 실제 이동 방향·속도·캐릭터 크기를 반영해 발 궤적과 보폭을 맞춘다. 프레임 사이 그림이 유지되는 시간에도 몸은 움직이므로, 원화가 바뀌는 순간만 검사해서는 부족하다.
4. 흙↔도로·철도 경계를 두 발이 걸쳐 지날 때를 확인한다. 중심 높이만 갑자기 바뀌어 몸 전체가 튀면 접촉 상태에 맞춘 높이 전환을 넣는다. 두 발의 높이 차가 눈에 띄는 경우에는 전신 그림 하나를 올리는 보정만으로 해결되지 않으므로 해당 발 디딤 자세도 필요하다.
5. 바닥, 캐릭터, 건물 기초·전경, 그림자를 나눠 가림을 검사한다. 발을 항상 맨 앞으로 그리거나 몸을 일괄 띄우는 보정은 다른 위치에서 잘못된 가림을 만들 수 있다.
6. 그 자리에서 정지·출발·방향 전환까지 확인한다. 발이 공중에 있던 자세에서 대기로 즉시 바뀌면 마지막 디딤과 체중 회수 자세를 연결한다.

## 3. 방향·동작·캐릭터의 일관성

### 참고 자료에서 확인한 방법

[SLYNYRD: Top Down Character Animation](https://www.slynyrd.com/blog/2025/3/24/pixelblog-55-top-down-character-animation)은 방향별 캐릭터를 같은 위치에 맞춰 회전 재생하고, 여러 방향의 동작을 같은 보행 시점으로 맞춰 비교한다. 머리 높이·어깨·팔다리 길이의 불일치를 찾아 고친다. 자료의 작은 달리기 캐릭터는 비교 방법의 참고이며 TownGrid의 체형·해상도 규격은 아니다.

[Spine 공식 담당자의 아이소메트릭 제작 설명](https://en.esotericsoftware.com/forum/d/13250-isometric-character)은 앞면과 뒷면의 자산 배치·가림 순서를 맞추고 발 동작을 다시 조정하도록 안내한다. 방향을 바꿔도 한 방향의 그림 변형을 그대로 복사해 끝내는 방식은 부족하다.

### TownGrid 적용안

- 네 방향을 동시에 재생하고, 같은 시점에 같은 다리가 체중을 받는지 확인한다. 카메라만 회전할 때는 보행 진행을 유지한다. 실제 캐릭터가 방향을 틀 때는 디딤과 체중 이동이 필요하다.
- 보행 중 정지, 정지 후 출발, 걷기↔운반, 들기→운반→놓기, 피격 후 복귀를 별도로 확인한다. 현재 `characterPose`의 일반 걷기→대기 전환은 마지막 디딤을 완료하는 전용 전환 없이 클립을 바꾼다.
- 같은 종의 의상만 바뀌어도 가려지는 팔·소매·장비를 개별 확인한다. 드워프·티탄·켄타로스·부유형은 자기 비례와 이동 방식에 맞는 동작을 만든다. 통일할 것은 품질·방향·접촉 기준이며 모든 몸에 같은 보폭과 팔 궤적을 복사하는 것이 아니다.
- 반전 방향에서 비대칭 의상·장비·사용하는 손이 문제가 되면 그 방향의 작화를 보정한다.
- 전체 캐릭터에 같은 확인표를 적용한다. 한 캐릭터의 통과를 나머지 캐릭터의 완료로 확장하지 않는다.

## 기존 검사에 추가할 시각 확인

현재 `tests/gait-anatomy.py`는 다리의 투영 길이와 교대 시점을 검사한다. `tests/cast-locomotion.py`는 관절·접점 메타데이터를 주로 읽으며, 화면상 발 검사도 전체 불투명 픽셀 중 가까운 점과 가장 잘 맞는 지지발을 사용한다. 양발의 실제 그림이 모두 자연스럽다는 검사는 아니다. `tests/cast-locomotion-browser.mjs`의 바닥 관통 검사는 높이를 바꾼 평면을 사용하므로 지형 경계와 건물 앞뒤를 포괄하지 않는다.

아래 항목은 아직 완료되지 않은 추가 확인 범위다.

| 구분 | 확인 장면 | 통과 기준 |
|---|---|---|
| 형태 | 투명 배경, 정상 속도·느린 재생 | 팔·손·소매·무릎이 끊기거나 눌리지 않고 전신이 함께 움직임 |
| 접지 | 눈금 바닥, 좌우 발 표시 | 각 지지 구간에서 발이 밀리지 않고 뒤꿈치→발바닥→발끝이 연결됨 |
| 이동 | 실제 경로, 여러 속도 | 프레임 사이에도 이동 속도와 발 궤적이 어긋나 보이지 않음 |
| 표면 경계 | 흙↔도로·철도, 건물 기초 주변 | 몸이 튀지 않고 발 관통·공중 부양이 없음 |
| 가림 | 건물·나무 앞뒤, 네 카메라 방향 | 앞에 있는 주민이 가려지거나 뒤에 있는 발이 뚫고 나오지 않음 |
| 전환 | 출발·정지·회전·상하차·피격 복귀 | 디딤이 끊기지 않고 손·짐의 위치가 튀지 않음 |
| 방향 | 네 방향 동시 재생, Q/E | 같은 보행 시점과 체형을 유지함 |
| 전원 | 51명·11동작·네 방향 | 빈 항목 없이 개별 확인하며 사람형·네발형·부유형을 구별함 |

판정은 실제 게임 크기의 정상 속도에서 먼저 한다. 확대·느린 재생·수치 검사는 실패한 부분을 찾는 데 쓴다. 프레임 존재와 자동 검사 통과만으로 시각 완료를 판정하지 않는다.

## 구현 순서

1. 같은 장면에서 형태·접지·가림을 구분할 수 있는 비교와 발 추적을 준비한다.
2. 기존 미라 디자인으로 걷기·운반·출발·정지·회전의 연속 작화를 완성하면서 실제 지면에 맞춘다. 앞면만 끝내지 않고 네 방향을 함께 확인한다.
3. 드워프·티탄·켄타로스·부유형에서도 성립하도록 체형별 동작을 만든다.
4. 51명 전체의 나머지 직업 동작·인사·상하차·공격·피격·쓰러짐까지 진행하고, 각자의 모든 동작과 전환을 위 표로 확인한다.

추천 방식은 **기존 디자인을 유지한 2D 프레임별 동작 작화와 실제 게임의 접지·가림·전환 수정**이다. 필요한 자세와 중간 작화의 제작·검수가 남아 있으며, 현재 생성 초안이나 기존 관절 프레임이 그 작업을 대신 완료한 상태는 아니다.

## 화면 표시와 동작 효과(2026-10-07)

동작 작화와 별도로, 같은 그림이 화면에서 덜 깨지고 움직임이 더 잘 읽히게 하는 처리를 넣었다. 동작 원화의 품질 문제는 이것으로 해결되지 않는다.

- **표시 방식**: 주민 그림은 128px 칸이 화면에서 20~70px로 줄어드는 일이 많다. 예전에는 축소 단계 이미지 없이 가장 가까운 픽셀만 골라 걸을 때마다 픽셀이 빠졌다 생기며 반짝였다. 이제 `pixel-sampling.js`가 축소 단계 이미지(밉맵)와 확대용 경계 보정 셰이더를 쓴다. 확대하면 원화 픽셀이 같은 크기의 네모로 유지되고, 축소하면 평균한 색을 한 단계 선명하게 고른다. 색은 미리 곱한 알파로 거른다. 건물, 나무, 차량, 동물처럼 화면을 향해 서는 환경 그림도 같은 방식을 쓰며, 지면 표면은 프레임 경계 번짐을 막으려고 예전 방식을 유지한다. CPU 렌더러는 주민 그림만 축소할 때 부드럽게 그린다. 밉맵 때문에 그림 한 장의 그래픽 메모리가 약 3분의 1 늘었다.
- **동작 효과**: `character-effects.js`가 실제로 보이는 프레임을 읽어(관절 리그는 발별 접지, 브론은 지지발 전환, 도구 자료가 없으면 손목이 가장 낮은 프레임) 발이 땅에 닿는 순간의 먼지, 도구가 닿는 순간의 불티와 조각, 짐을 내려놓는 순간의 먼지, 피격 불꽃, 쓰러질 때의 흙먼지를 그린다. 먼지 색은 눈, 모래, 길, 흙을 따른다. 피격 때는 그림이 0.14초 동안 하얗게 번쩍이고 0.3초 동안 옆으로 밀렸다 돌아온다. 저장하지 않고, 동작 줄이기 설정과 먼 화면에서는 그리지 않는다.
- 효과 화면은 `/world-effects-preview.html?effect=characters`, 확인 그림은 `docs/verification/character-render-20261007/`이다. 시험은 `tests/character-effects.mjs`(51명 네 방향의 발 착지와 타격 순간)와 `tests/world-effects-browser.mjs`다.
